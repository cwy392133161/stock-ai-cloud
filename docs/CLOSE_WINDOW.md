维修后正式验证必须显式设置 skip_ai=true。该选项默认仍为false，既有定时AI行为没有变更；不要把“有跳过选项”误解为默认不会调用付费模型。显式跳过会显示“按要求跳过AI”，而不是错误地显示模型失败。

## 定时任务严重延迟或重跑

2026-11-11和11-12的定时运行实际分别在17:04 UTC、17:33 UTC创建，执行时间已经是北京时间次日凌晨。定时表达式仍是 `10 9 * * 1-5`，但 GitHub 不保证准点触发。工作流记录实际执行时点，不猜测缺失的原计划触发时点。

- 定时任务在北京时间工作日17:00至24:00以外执行时，标记 `schedule_missed_window`。它不会读取行情或调用AI，也不会把前一日数据换成次日日期。状态写入后，本次工作流以失败结束，不能用绿色空跑表示完成。
- 同一 `schedule` 运行的执行次数大于1时，标记 `schedule_repeat_blocked`，阻止再次采集或调用AI。该保护只适用于执行本版代码的同一运行重试，不会改变旧提交上的历史运行，也不保证不同运行ID或手动运行之间全局只执行一次。
- 执行次数缺失或无效时同样停止。普通手动 `workflow_dispatch` 的既有收盘窗口及 `report_only` / `skip_ai` 行为保持不变；不会自动转成补跑。
- 首页和研究页同时保留行情失败、AI待复核和本次未执行原因。`last_schedule_observed_at` 是实际检查时间，`last_schedule_run_id` / `last_schedule_run_attempt` 用于追查运行，均不是行情时间。
- 未新增定时表达式、自动重跑或补偿AI调用。GitHub未创建运行时，本代码没有执行机会，也不能自行修复调度平台的延迟。需要从Actions记录区分“尚未触发”“错过窗口”和“真正采集失败”。

不使用次日凌晨实时接口来冒充前一日历史收盘数据：A/H数据检查目前要求报价日期与实际检查日期一致，已发布快照也记录实际生成时点。若未来需要跨日补采，必须先实现可验证的交易日及历史数据来源、双市场同日校验、单独的采集时间和报价时点、持久去重及明确费用边界，不能仅放宽现有时间门槛。
