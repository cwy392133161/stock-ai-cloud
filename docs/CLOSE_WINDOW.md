# 收盘发布窗口与盘中诊断

Daily 工作流生成 A 股收盘榜单。正式采集窗口在北京时间工作日 17:00 开放，计划触发时间为 12:30（UTC 04:30），提前启动的作业等至当天 17:00。正式评分前检查报价日期、收盘时间和数据完整性。

17:00前手动运行 Daily：
- 不读取全市场行情、不重新选股、不自动调用AI。
- 保留原 data.json，只更新“等待收盘窗口”状态，不误报数据源故障。
- 需要盘中排障时使用 read-only source validation 或 market probe；它们不发布、不调用AI，盘中字段覆盖不足仍应失败，不降低收盘质量门槛。

原因：2026-11-10的旧主程序在12:45手动启动，A股行情通过；港股午间成交覆盖68%，未达到原75%门槛，重复同源采集耗时30分钟。这不是应把门槛改低的依据。

维修后正式验证必须显式设置 skip_ai=true。该选项默认仍为false，既有定时AI行为没有变更；不要把“有跳过选项”误解为默认不会调用付费模型。显式跳过会显示“按要求跳过AI”，而不是错误地显示模型失败。

## 定时任务严重延迟或重跑

2026-11-16 至 11-20 的五次定时运行比原计划 17:10 晚约 8 小时 35 分至 10 小时 23 分。改为单个工作日定时点 `30 4 * * 1-5` 后，把相同延迟带入测试，预计启动时点落在当天 21:05–22:53。实际触发时刻仍取决于 GitHub。

- 只读等待作业接受北京时间工作日 12:30 后启动的一次执行，最多等待 4.5 小时。采集作业须拿到同日放行记录，并在采集前再次核对 17:00–24:00 窗口。等待作业独立于选股与提交的并发组。日期有效的定时运行若发现主分支已推进，会停止采集。
- 凌晨、周末，或等待后才启动且跨日的采集作业标记 `schedule_missed_window`。状态写入后工作流以失败结束，不回填旧行情。GitHub 未提供原定触发时间，无法从事件判断所有超过一天的极端延迟；放行日期仅代表实际观察到的北京时间日期。
- 同一 `schedule` 运行的执行次数大于1时，标记 `schedule_repeat_blocked`，阻止再次采集或调用AI。该保护只适用于执行本版代码的同一运行重试，不会改变旧提交上的历史运行，也不保证不同运行ID或手动运行之间全局只执行一次。
- 执行次数缺失或无效时同样停止。普通手动 `workflow_dispatch` 的既有收盘窗口及 `report_only` / `skip_ai` 行为保持不变；不会自动转成补跑。
- 首页和研究页同时保留行情失败、AI待复核和本次未执行原因。`last_schedule_observed_at` 是实际检查时间，`last_schedule_run_id` / `last_schedule_run_attempt` 用于追查运行，均不是行情时间。
- 仍使用单个工作日触发，无自动重跑。准点运行会占用 GitHub 托管 runner 约 4.5 小时。GitHub 完全漏触发时没有运行可等待，超过约 11.5 小时的延迟也可能错过窗口。需在 Actions 中区分“尚未触发”“错过窗口”和“真正采集失败”。

日常 A 股采集按实际交易日校验报价。历史归档分别记录报价时点和采集时间，回算榜单时使用归档日期对应的行情。

参考：[GitHub 定时事件说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) · [托管 runner 作业时限](https://docs.github.com/en/actions/reference/limits)。
