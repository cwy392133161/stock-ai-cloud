# 收盘发布窗口与盘中诊断

Daily 工作流生成 A 股收盘榜单。正式采集窗口在北京时间工作日 17:00 开放，计划执行时间为 17:10。正式评分前检查报价日期、收盘时间和数据完整性。

17:00前手动运行 Daily：
- 不读取全市场行情、不重新选股、不自动调用AI。
- 保留原 data.json，只更新“等待收盘窗口”状态，不误报数据源故障。
- 需要盘中排障时使用 read-only source validation 或 market probe；它们不发布、不调用AI，盘中字段覆盖不足仍应失败，不降低收盘质量门槛。

原因：2026-11-10的旧主程序在12:45手动启动，A股行情通过；港股午间成交覆盖68%，未达到原75%门槛，重复同源采集耗时30分钟。这不是应把门槛改低的依据。

维修后正式验证必须显式设置 skip_ai=true。该选项默认仍为false，既有定时AI行为没有变更；不要把“有跳过选项”误解为默认不会调用付费模型。显式跳过会显示“按要求跳过AI”，而不是错误地显示模型失败。

## 定时任务严重延迟或重跑

2026-11-11和11-12的定时运行实际分别在17:04 UTC、17:33 UTC创建，执行时间已经是北京时间次日凌晨。定时表达式仍是 `10 9 * * 1-5`，但 GitHub 不保证准点触发。工作流记录实际执行时点，不猜测缺失的原计划触发时点。

- 定时任务在北京时间工作日17:00至24:00以外执行时，标记 `schedule_missed_window`。它不会读取行情或调用AI，也不会把前一日数据换成次日日期。状态写入后，本次工作流以失败结束，不能用绿色空跑表示完成。
- 同一 `schedule` 运行的执行次数大于1时，标记 `schedule_repeat_blocked`，阻止再次采集或调用AI。此处的窗口保护只适用于同一运行重试；新增交易日执行账本在采集/AI前另行阻止不同运行ID与手动入口的重复执行，不改变旧提交上的历史运行。
- 执行次数缺失或无效时同样停止。普通手动 `workflow_dispatch` 的收盘窗口不放宽；`report_only` / `skip_ai` 入口还受交易日账本约束，已有尝试不会自动重做；同日skip_ai成功发布后，仅凭完整持久证据与相同新鲜快照，report_only可在同一发布窗口内认领一次AI阶段，未知状态、旧/异日快照拒绝。不会自动转成补跑。
- 首页和研究页同时保留行情失败、AI待复核和本次未执行原因。`last_schedule_observed_at` 是实际检查时间，`last_schedule_run_id` / `last_schedule_run_attempt` 用于追查运行，均不是行情时间。
- 未新增定时表达式、自动重跑或补偿AI调用。GitHub未创建运行时，本代码没有执行机会，也不能自行修复调度平台的延迟。需要从Actions记录区分“尚未触发”“错过窗口”和“真正采集失败”。

日常 A 股采集按实际交易日校验报价。历史归档分别记录报价时点和采集时间，回算榜单时使用归档日期对应的行情。

持久化权限、失败/中断状态及人工恢复审计见 [交易日执行账本](DAILY_EXECUTION_LEDGER.md)。
